Captain directive · single app model

Web and Android are ONE app — not two apps

Yes, this makes sense. There is no per-platform schema, capability, or wiring split. Both clients hit the same backend contract, the same Firebase project, the same Data Connect / Cloud SQL / Firestore state. The consequence for wiring:

  • One shared backend URL for both clients — Android backendBaseUrl and web /api/* point at the same hosted backend (via https://spresso-5561f.web.app). No divergence.
  • User identity = Firebase Auth UID, shared across devices. Log in on web → the same user (and their orders/state) is visible on mobile, and vice versa. All order state is keyed by UID, never device-bound.
  • Orders must be user-scoped everywhere — GET /api/orders?userId=… + Firestore /users/{uid}/orders/{orderId} (already the rule) so both platforms see identical order state.
  • Same capabilities on both — whatever route the web app uses, Android uses the same route (products, lens-search, purchase/confirm, try-on, spin360, live-chef). No platform-only surface.

One app · one order state

OrdersTracker reads root Firestore orders

OrdersTracker.tsx:25 → getDocs(collection(db, "orders")) against firestoreDatabaseId=ai-studio-spresso-…. firestore.rules only allow /users/{userId}/orders/{orderId} (owner), /logs, /chats, /users/{userId}. Root orders is default-deny → the client read fails in production. Server writes root orders via admin SDK (bypasses rules). RE-HOME: both web and Android read/write orders through the uid-keyed API + user-scoped Firestore paths, so login on either device shows the same orders.

Zero-mock + wrong endpoint

Kitesurf purchase automation is not implemented correctly

kitesurfService.ts (drives /api/purchase/automate) has two defects per the official Cloudflare Kitesurf / Browser Run docs: (1) ZERO-MOCK VIOLATION — when Cloudflare secrets are missing or the API fails, it falls back to a "high-fidelity edge simulator" (lines 98-115) that fabricates checkout steps and a hardcoded Unsplash receiptUrl, returning success:true; (2) wrong endpoint — it calls the /screenshot Quick Action (browser-run/screenshot?browser=kitesurf) which only renders/captures an image and CANNOT click, fill forms, or submit checkout, yet the code logs fabricated DOM-click/address/payment steps. Correct setup: use Quick Actions (/scrape, /crawl, /json, /markdown, /content) for autonomous search/scraping, and CDP via puppeteer-core (wss://api.cloudflare.com/client/v4/accounts/<ACCOUNT_ID>/browser-run/devtools/browser?browser=kitesurf) for real add-to-cart → checkout automation; secrets (CLOUDFLARE_ACCOUNT_ID, CLOUDFLARE_API_TOKEN) are read via getSecret but missing from .env.example; token needs Browser Rendering - Edit permission. Limits: Workers Free = 10 browser-min/day, 3 concurrent, Quick Actions 1 req/10s; Workers Paid = no browser-hour cap, 120 concurrent — required for HA scale. Caveat: Kitesurf cannot pass bot-challenge/TLS handshakes or hold long-lived auth sessions — plan checkout automation against compatible stores.
